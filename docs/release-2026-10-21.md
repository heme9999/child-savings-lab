## Interface and publication changes

| Before | After | Why |
| --- | --- | --- |
| Page titles were used as `WebSite.name`, including on inner pages | One homepage `WebSite` named Child Savings Lab; `WebPage`/`Article` entities reference its stable ID | Keep the neutral publication identity distinct from individual landing pages |
| Homepage and tools-directory headings were slogans | Descriptive child-savings headings; homepage primary action directly opens the tools directory | Make purpose and the next click clearer without narrowing the brand to one policy |
| Growth amount began about 831px down a 390px viewport; submit about 1446px down | Amount about 477px; primary submit about 771px, bottom 821px in a 390×844 viewport | Put the central operation inside the tested first screen |
| Secondary assumptions lengthened the basic form | Native disclosures, visible live summaries of dates/pilot/balances/fees, and nearby submission actions inside advanced sections | Shorten the initial path while keeping all assumptions editable and validated |
| Checker submit began about 1549px down | Basic account-status submit about 845px; separate review/authority and pilot disclosures retain every answer and qualifier | Allow an account-status path without guessing unknown pilot answers; a complete pilot workflow still has a nearby action |
| Sparse tool-use guidance and no sharing images | Three-step instructions, four concrete capabilities, six behavioral questions per tool, and three 1200×630 PNG cards | Explain actual utility and sharing scope without keyword stuffing, rich-result promises, or forecast claims |
| Publisher transparency relied mainly on disclaimers | Links to source records, editorial process, and three reproducible calculation examples | Make claims inspectable without inventing credentials, an author name, or professional sign-off |
| Regression checks covered HTML and crawl resources | Additional publication/schema/social checks and every built JS/CSS chunk plus sharing images checked by GET/HEAD, MIME, and SHA-256 | Catch asset fallbacks, stale shared chunks, and broken preview images |

Sharing images are code-native artwork generated by `npm run generate:social`; their PNG outputs are committed. The existing sharp version is pinned as a development dependency. The verified Cloudflare account is specified using `CLOUDFLARE_ACCOUNT_ID` in the deployment command to avoid ambiguity when two accounts are available, following the [Pages direct-upload guidance](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/). Pages configuration does not support an `account_id` key: the initial deployment validation rejected that key before publication, and it was removed before retrying. A regression test now rejects that unsupported configuration and checks the deploy-command gates.
